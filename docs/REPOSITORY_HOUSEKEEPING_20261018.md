**性质：维护操作入口。** 本文不更改任何史实、地图几何或已批准网站操作。首次整理先清点和建索引，经过对账再关闭旧PR或删除分支。对话中的“已完成”只能以实际合并主干及GitHub Pages部署结果为准。

完整待审PR账本见 [开放PR逐项清点](OPEN_PR_TRIAGE_20261018.md)。最新正式出版章节必须查询 `data/chapters.json`，不能用旧版README下半部或旧主编日志推断。

## 二、正式项目结构：不做破坏性整体搬家

| 范围 | 角色 | 清理原则 |
|---|---|---|
| `index.html`、`app.js`、`css/`、`js/`、`assets/`、`style.css` | 正式网站前端 | 由已通过桌面UI回归的PR修改；不要为美观改动加载路径 |
| `data/chapters.json`、`data/atlas-*.json`、`data/stories/index.json`、`data/stories/`、正式`data/*.geojson` | 已发布历史记录及地图显示数据 | **唯一正式数据入口**；按来源、时间、主体、几何语义、稳定ID增量修改 |
| `research/` | 原始研究、史料、候选GIS、未核事件和跨年代承接 | 研究产物不得被前端自动视为已经发表；不可为“清爽”删除证据 |
| `editorial/` | 主编审查、出版决策、交接与质量说明 | 每次合并记录包含纳入/拒绝/暂缓的结论 |
| `docs/` | 稳定规则、技术说明和审核报告 | 维护指南与实时PR清单在这里；避免在根目录新堆众多STATUS文件 |
| `scripts/`、`.github/workflows/` | 自动检验、浏览器测试和Pages发布 | 优先修复失效测试及重复触发；不要在未经完整验收前将现有13个工作流整体重写 |
| `patches/` 与根目录旧预览文件 | 原型和历史兼容 | 确认引用/用途后才能搬迁；与正式运行路径不可混为一谈 |

严禁为了使文件树变短而重命名全部 `data/`，更不能改变已批准的桌面地图双开关、年度推进、来源点击或不确定版图虚线语义。

## 三、把每个PR分为四种生命周期

1. **正式发布变更**：实际修改 `data/` 或页面/JS/CSS；需要章节/长文测试、来源核对、严格空间检查、实际Chromium桌面截图。用户/主编验收后才能进 `main`。
2. **研究底稿**：只存证据，标记 `research-only / 待主编采纳`；缺乏可确认历史边界时，禁止把假设Polygon作为实际占领面。有价值的底稿可以长期保留，但不得冒充正式发布。
3. **已吸收/仅需归档**：逐项对比主干版本、事件ID、史料索引及来源完整性；已吸收的标出主干提交SHA，未吸收的保留分支入口；确认后可以关闭PR，但**关闭不代表将内容合并**。
4. **冲突/重复/失效旧实现**：记录替代的主干实现和核查证据；关闭过时界面PR时不进行整分支合并。没找到替代证据之前不能删除。

**每份待关闭PR必须先写出**：本次处理结果、是否将研究成果迁移到有长期入口的位置、替代PR/提交SHA或未解决Issue、原分支可追溯链接。批量关闭、强行Squash所有研究包、批量删除未合并分支均被禁止。

## 四、后续AI/编辑的最低交接要求

- 开始工作先读取：`AGENTS.md` → `data/chapters.json` → `data/stories/index.json` → 本目录的PR对账表 → 对应年代研究与最新主编记录。
- 创建任务分支建议统一按 `research/<period>-<topic>-<date>`、`editorial/<topic>-<date>`、`fix/<bug>-<date>`、`maintenance/<scope>-<date>` 命名。**现有158条旧分支不应为了统一名字集体改名**。
- 一个PR只聚焦一个可解释的历史专题、研究包或维护缺陷；明确标注 **研究候审** / **正式上线候审** / **纯维护**，且主基线统一以 `main` 为准。历史上PR #14针对另一研究分支，是特例，应先检查依赖，不自动改base。
- 涉及超长历史事件，保留跨世纪 `stable_id` / related事件 / 续接索引；新世纪不重新发明同一事件。未知界线用虚线、不要把战争影响线变成征服面积。
- 每次交付记录：新增或修改文件、史料出处、精度限制、与正式记录去重结果、测试记录URL、PR链接、当前未解决问题和下一步。
- 数据异常 `ERROR` 应阻断合并/发布，史料有争议的 `REVIEW` 待审保留；不为追求“全绿”杜撰数据。参见维护PR #164。

## 五、推荐的实际清理顺序

**第一批（无损）：** 建立本目录和PR台账，给README一个入口；识别31个PR与现有主干的关系；暂时不关闭、不删除、不移动生产代码。

**第二批（审查旧PR）：** 先处理 #41/#39/#38 三份旧地图界面PR与 #47 制图治理PR的差异；它们动了前端/CI文件，不能被旧内容覆盖。再审 #82 地理保护、#118/#124 重大专题，做史料和事件去重。

**第三批（研究归档）：** 分时期审核 #1—#61 研究底稿；对于主干已有章节，只迁移经核对的增量；给PR标注“待调查”“已吸收”“仍有独家档案”等状态。不要因为年代已发布就把研究PR全关掉。

**第四批（分支清仓）：** 仅对已有合并/归档证据且无未保存独特文件的分支，逐条确认后删除。保留 `main`、获批UI基线、未合并资料分支、17世纪活跃分身以及受保护或其他AI仍在使用的分支。必要时先在可长期访问的 `research/` 目录归档。

**第五批（CI与根目录）：** 比较13个工作流的重复测试、触发条件及通知噪声；稳妥简化而不降低质量。旧原型、根目录资料说明和历史日志须先检查所有静态引用，后续独立PR逐项搬迁。

**验收定义**：主干有一个可信的正式入口；每个开放PR有清楚用途和后续动作；每个活跃分支有负责事项；旧研究成果可追溯；Pages与桌面测试持续通过；没有删除真实史料或把示意区误作殖民领地。
